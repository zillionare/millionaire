## 结论摘要
- issue #17 的本质不是单纯改文案，而是要决定 Millionaire 只作为外部品牌，还是连 Python 包命名空间、默认配置目录、环境变量前缀、URL 前缀一起改掉。
- 当前仓库里 `quantide` 同时承担了多个技术标识角色：Poetry 包名、顶层 import namespace、启动入口、运行时默认 URL 前缀、默认数据目录 `~/.quantide`、配置目录中的 `quantide.db` / `.quantide.pid`、以及 `QUANTIDE_ENABLE_DEV_STUBS` 等环境变量。
- 代码盘点结果：仅 `from quantide` / `import quantide` 就覆盖 154 个 Python 文件；全仓与品牌/命名相关的命中约 878 处；其中源码 88 个文件、测试 66 个文件、配置路径/环境变量相关命中 39 处。

## 关键证据
- `pyproject.toml` 当前发行名为 `quantide`，且只打包 `quantide/` 目录。
- `quantide/config/paths.py` 默认数据目录为 `~/.quantide`，配置目录内文件名包括 `quantide.db` 与 `.quantide.pid`。
- `quantide/config/dev_stubs.py` 使用环境变量 `QUANTIDE_ENABLE_DEV_STUBS`。
- `quantide/data/models/app_state.py` 与 `quantide/config/settings.py` 默认 `app_prefix` 为 `/quantide`。
- `quantide/web/apis/broker.py` 通过 `version("quantide")` 读取发行版本，发行包名一旦变为 `quantide-millionaire`，这里必须同步调整。
- `start.sh`、`README.md`、`docs/developer-acceptance.md`、`tox.ini`、`tests/test_app.py`、`tests/config/test_paths.py` 都把 `quantide` 当作真实技术标识，而不只是产品品牌。

## 风险与代价评估
1. 仅做外部品牌换新：改仓库 slug、README/docs/UI 品牌文案、发布包名，保留内部 namespace `quantide`。这是低到中风险，约 0.5 到 1.5 天。
2. 再顺手抽离品牌常量，把展示层品牌与技术标识解耦，但仍不改 import namespace / 数据目录 / 环境变量。这是中风险，约再加 0.5 到 1 天。
3. 全量硬改：把 `quantide` 连同包目录、import namespace、配置目录、默认数据目录、环境变量、URL 前缀全部切到 Millionaire。这是高风险，约 2 到 4 天开发加 0.5 到 1 天回归；虽然当前版本仍是 0.1.0，不必做向后兼容，但内部改动面依然很大。

## 推荐方案
- 把 issue #17 收敛为“外部 re-branding”问题：仓库/工作区名改为 millionaire，UI 与文档品牌改为 Millionaire，发布包名改为 `quantide-millionaire`。
- 保留内部 Python namespace `quantide`，不要在同一个 issue 中连 `~/.quantide`、`QUANTIDE_*`、`/quantide` 一起改。
- 额外补一个小型重构：集中定义品牌文案常量，把展示层名称与技术常量分离。这样后续再换品牌，不会再次扫全仓。
- 如果未来确实要做“内外一致”的彻底更名，单独开一个 dedicated refactor issue，在正式发布前一次性 hard cut，而不要把它混进当前 branding issue。
