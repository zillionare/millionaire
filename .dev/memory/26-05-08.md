# 2026-05-08 对话记录

## 用户需求

1. 阅读最近的提交历史，以及 `.dev/specs` 和 `.dev/memory` 文档，并进入 deep-interview 模式。
2. 评估当前系统离“可发布、可长期运行的量化产品”还有多远，但暂不考虑 gateway 现有 issue 和 UI 风格问题。
3. 将本轮发布目标收敛为：单用户单机可发布，同时满足运维级可靠性要求。

## 已确认约束

1. 发布评估暂不讨论现有 gateway 缺陷与 UI 风格设计，但 `paper/live` 仍必须在本地准备好可运行环境。
2. 发布目标选择为：提供本地模拟 gateway，使 `paper/live` 能跑通最小端到端链路。
3. 系统形态为单用户单机，但因量化交易资金风险高，仍需满足运维级可靠性要求。
4. 用户不能接受以下失败类型：
   - 回测结果不一致
   - 任务或数据下载中断后无法恢复
   - SQLite / Parquet 数据静默损坏
   - 订单链路契约与 gateway/stub 不一致
   - 日志与状态信息不足以定位问题
5. 对交易相关异常的要求是：`paper` 与 `live` 一旦出现异常，必须阻断相关操作，并在界面显著位置持续告警；用户关闭后仍需在可追溯位置再次查看。`backtest` 可以相对放松，但也必须有显著提示。
6. 本地 gateway stub 的目标不是简单 mock，而是尽量贴近 QMT 的协议和状态机。
7. 发布前验收必须以全自动端到端回归为主，并由专门的 test/QA 角色负责用户场景级验证。
8. 用户明确要求的发布前 E2E 场景至少包括：
   - 初始化
   - 数据下载与补齐
   - 策略发现/加载
   - 回测运行
   - paper 下单到成交
   - live 下单到成交
   - 异常告警与阻断
   - 任务恢复与重启恢复
9. 回测发布标准进一步收敛为：
   - 固定数据下结果必须完全可重复
   - 复权使用复权因子即可，不要求精确复权重建
   - 默认使用动态前复权
   - 撮合必须考虑手续费、涨跌停、停牌等市场约束
   - 手续费规则应由用户配置
10. `paper/live` 的本地 gateway stub 和验收状态机需要尽量贴近真实交易：
   - 委托进入撮合队列
   - 部分成交
   - 撤单
   - 废单
   - 拒单
   - 成交回报乱序或延迟
   - 断线重连后的状态补推
11. 主体系统的唯一订单主键确定为 `qtoid`；柜台或 gateway 返回的订单号只作为外部映射和排障字段，不与 `qtoid` 双主键并存。
12. 交易异常只阻断受影响账户/策略的自动交易，不做全局阻断；人工交易仍然允许。
13. 被阻断后，人工交易路径只展示持续告警，不再增加额外人工确认。
14. 发布态内置的 gateway stub 应以独立本地服务形态交付，而不是仅限进程内测试服务器。
15. 检测到 SQLite 或 Parquet 数据损坏时，默认阻断相关功能并进入只读诊断模式，不做自动修复后继续运行。
16. 阻断状态需要持久化；应用重启后如果仍检测到异常，则自动恢复阻断。
17. 用户关闭风险告警时，就视为解除阻断；但关闭动作必须经过二次确认，并明确提示自动交易会恢复执行。
18. 用户在确认关闭告警后，被阻断的自动交易策略恢复原状态运行；若系统再次检测到异常，则重新建立事件并重新阻断。
