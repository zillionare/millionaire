# 发布态收口规范

## 1. 文档定位

本文档定义 quantIDE 在当前阶段达到“可发布、可长期运行”所必须满足的发布态约束。

约束关系如下：

1. `.dev/specs/00-architecture.md` 仍是最高优先级的架构决议文档。
2. 本文档在“发布门槛、交易安全、恢复语义、QA 放行标准”上提供当前权威约束。
3. `.dev/specs/three_mode_acceptance_checklist.md` 负责记录当前证据、缺口与放行判定，不替代本文件。

本文档明确不讨论两类问题：

1. 现有 gateway 项目自身的缺陷修复细节。
2. UI 风格重做与视觉设计质量。

但即使不讨论上述两类问题，发布态仍必须满足本文件规定的本地 stub、阻断、恢复与验收要求。

## 2. 发布目标

当前阶段的发布目标定义为：

1. 系统形态是单用户单机，管理员用户固定为本地唯一操作者。
2. 系统必须满足运维级可靠性要求，因为量化交易异常会直接带来资金风险。
3. 同一份策略代码必须能够在 `backtest / paper / live` 三种模式下零修改运行。
4. 主体系统不直连 `xtquant/QMT`；`live` 的正式交易能力只能通过 gateway 提供。
5. `paper` 与 `live` 在发布前都必须具备可本地运行的端到端验收环境。
6. 发布前放行以全自动端到端回归为准，不能以人工口头确认替代。

## 3. 非协商约束

### 3.1 订单主键

1. `qtoid` 是主体系统唯一订单主键。
2. 柜台或 gateway 返回的订单号只作为外部映射字段与排障字段，不与 `qtoid` 双主键并存。
3. 订单、成交、告警、日志、恢复和 UI 跳转都必须能够回落到 `qtoid`。

### 3.2 交易异常处理

1. `paper` 与 `live` 中任何交易链路异常都必须触发阻断，而不能静默重试后继续运行。
2. 阻断粒度是“受影响账户/策略”，不是全局停机。
3. 被阻断后，不允许该账户/策略继续发出新的自动交易请求。
4. 被阻断后，实盘交易界面的人工操作仍然允许，但界面必须持续显示显著风险告警。
5. `backtest` 可以不进入交易阻断，但必须给出显著错误提示。

### 3.3 风险告警与解除语义

1. 交易异常触发后，页面顶部必须持续显示风险告警，直到用户显式处理。
2. 用户关闭风险告警后，事件不能消失，必须沉淀到独立的风险事件中心中供再次查看。
3. “关闭告警”与“解除阻断并恢复自动交易”是同一个动作。
4. 在真正关闭前，系统必须执行二次确认，并明确提示：自动交易将恢复执行，用户应确保系统已经完全恢复。
5. 如果用户取消关闭，则保持阻断，用户仍可继续进行人工交易。
6. 如果用户确认关闭，则当前阻断立即清除，原自动交易状态恢复。
7. 一旦系统再次检测到相同或新的异常，应重新建立事件并重新阻断。

### 3.4 持久化与重启恢复

1. 风险事件与阻断状态必须持久化。
2. 应用重启后，如果系统检测到相关异常仍然成立，则必须自动恢复阻断状态。
3. 应用重启后，如果用户此前已显式关闭告警，则不应仅因历史事件自动重建阻断；只有在重新检测到异常时才再次阻断。

### 3.5 数据损坏处理

1. 一旦检测到 SQLite 或 Parquet 数据损坏，不得自动修复后继续运行。
2. 系统必须阻断相关功能的写操作、自动交易、回测执行和后台任务写入。
3. 系统必须保留只读诊断、查看、导出和修复入口。

## 4. 回测发布标准

发布态对回测的最低要求如下：

1. 固定输入数据下，回测结果必须完全可重复。
2. 复权使用复权因子即可，不要求重建更高精度的复权模型。
3. 回测默认使用动态前复权。
4. 撮合必须考虑手续费、涨跌停、停牌等市场约束。
5. 手续费规则由用户配置。
6. 回测失败或数据异常时，必须给出显著提示而不是静默返回空结果。

## 5. Paper / Live 交易安全与恢复要求

### 5.1 交易状态机

发布态的 `paper / live` 本地验收必须覆盖接近真实交易的状态机行为，至少包括：

1. 委托进入撮合队列。
2. 部分成交。
3. 撤单。
4. 废单。
5. 拒单。
6. 成交回报乱序或延迟。
7. 断线重连后的状态补推。

### 5.2 触发阻断的典型异常

以下情况至少应被视为阻断候选：

1. 下单已发出但回报缺失或长期未闭合。
2. `qtoid` 与外部订单号映射断裂。
3. 重连后订单/成交状态与本地状态不一致。
4. 交易账户、持仓、资产或订单回报出现不可解释的结构性缺失。

## 6. 本地 Gateway Stub 要求

1. 发布态必须提供一个独立运行的本地 gateway stub 服务。
2. 该 stub 不是简单的 `/ping` 健康检查服务，而是用于 `paper / live` 本地端到端验收的近真实交易环境。
3. stub 的协议与状态机应尽量贴近 QMT/gateway 的正式路径。
4. stub 至少需要提供以下能力：
   - 连接或最小鉴权能力
   - 账户、资产、持仓、订单、成交查询
   - 买入、卖出、撤单
   - 行情 WebSocket 推送
   - 状态补推与断连恢复
5. stub 必须支持可脚本化场景装载，使 QA 能用固定剧本复现部分成交、乱序回报、拒单、废单和重连恢复场景。
6. `paper` 的发布态 E2E 可继续使用本地主体仿真撮合，但必须通过 stub 提供实时行情、断连与异常注入能力；`live` 则通过 stub 提供交易与行情完整链路。

## 7. 风险事件中心要求

系统必须提供独立的风险事件中心，而不是仅依赖消息中心。

该中心至少需要满足：

1. 可以查看当前未关闭风险事件。
2. 可以查看历史已关闭风险事件。
3. 支持按账户、策略、时间、状态、事件类型查询。
4. 每条事件都能关联到 `qtoid` 及必要的外部订单号映射。
5. 每条事件都能查看触发原因、阻断范围、关闭信息和诊断上下文。

## 8. QA 放行标准

发布前必须由专门的 test/QA 角色维护并执行全自动 E2E。`executor` 可以维护单元测试和模块测试，但不能以此替代 QA 放行。

发布前至少必须覆盖以下 8 条端到端主链路：

1. 初始化。
2. 数据下载与补齐。
3. 策略发现/加载。
4. 回测运行。
5. `paper` 下单到成交。
6. `live` 下单到成交。
7. 异常告警与阻断。
8. 任务恢复与重启恢复。

如果上述任一链路缺少自动化证据，则当前版本不能宣称达到发布前验收完成状态。

## 9. 发布阻塞项定义

出现以下任一情况时，应直接判定为当前版本不可发布：

1. `paper` 或 `live` 没有本地独立 stub 支撑的端到端自动验收。
2. `qtoid` 无法作为唯一主键贯穿订单、成交、告警和恢复流程。
3. 交易异常不能触发账户/策略级自动阻断。
4. 风险告警不能持续显示，或关闭后无法在风险事件中心追溯。
5. 重启后阻断状态不能正确恢复。
6. 检测到数据损坏后系统仍继续写入或继续自动交易。
7. 发布前缺少 QA 维护的全自动 E2E 证据。
