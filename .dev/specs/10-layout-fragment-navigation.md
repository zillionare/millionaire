# 共享布局 Fragment 导航与 SPA-like 交互

## 1. 文档定位

本 spec 约束 quantIDE 在共享布局层的页面导航与渲染机制，目标是在不引入前端路由器、不迁移前端框架的前提下，以尽量少的改动获得更接近单页应用（SPA）的交互体验。

本 spec 受以下文档约束：

1. `.dev/specs/00-architecture.md`
2. `.dev/specs/03-layout-nav-style.md`

若与旧实现或历史讨论冲突，以本 spec 为准。

## 2. 背景

当前 UI 技术栈已经是 FastHTML + MonsterUI，并且项目内部已经广泛使用 HTMX 做局部更新。

例如：

1. 初始化向导已经通过 `hx_target` 在单页面容器内切换步骤。
2. 策略页内部已经存在局部刷新和 OOB 更新用法。
3. 中间件层已经识别 `HX-Request`，说明系统并不排斥“普通请求返回完整页、HTMX 请求返回 fragment”的模式。

与此同时，`.dev/specs/03-layout-nav-style.md` 已明确指出：

1. UI 采用 Header + Sidebar + Main 三栏布局。
2. 系统目标是具备现代化单页应用（SPA）的交互体验。
3. 当二级菜单变化时，main content 区应跟着改变。

但当前实际实现中，顶部导航和左侧菜单的大多数跳转仍然是普通页面导航。用户点击后，浏览器会重新请求并重绘整个页面，因此在系统维护、数据维护、策略等高频切换场景中，会明显出现：

1. header 跟着刷新。
2. sidebar 跟着刷新。
3. main content 整块重绘。
4. 页面有闪烁和“整页换页”的观感。
5. 交互体验不符合既有 spec 对 SPA 风格的目标。

因此，本次 spec 的任务不是引入真正的前端 SPA 架构，而是在当前技术栈下把“更像 SPA”的目标收敛为一套可执行、可约束、低侵入的导航与渲染方案。

## 3. 现状与根因

### 3.1 现状

当前共享布局由 `quantide/web/layouts/main.py` 中的 `MainLayout` 负责渲染。

绝大多数使用共享布局的页面，都会在路由处理时重新构造：

1. header。
2. sidebar。
3. main area。

当前导航的主要特点是：

1. header 一级导航多为普通链接。
2. sidebar 二级菜单多为普通链接。
3. 页面切换后由浏览器重新请求整个页面。
4. 页面内部虽然已有 HTMX 局部更新，但这些能力主要停留在单页面内部，没有提升到共享布局层。

### 3.2 根因

问题根因不在单个业务页，而在共享布局导航层缺少统一的 fragment 导航机制。

具体表现为：

1. 布局层没有统一处理“普通请求返回完整页、HTMX 请求返回 fragment”。
2. sidebar 激活态虽然由后端根据 URL 计算，但在局部导航时没有通过 OOB 机制回写旧页面。
3. header 与 sidebar 作为稳定壳层，没有被视作“尽量保持不重绘”的基础设施。
4. 新页面开发默认仍沿用普通页面导航，因此体验持续回到“整页重刷新”的路径。

## 4. 设计目标

本 spec 不追求把 quantIDE 改造成真正的客户端 SPA，而要求达到以下目标：

1. 点击 sidebar 子菜单时，只更新 main content，不整页刷新。
2. header 在此类切换中应尽量保持静止，不跟着重绘。
3. sidebar 激活项应准确切换，新激活项显示强调色，旧激活项移除强调色。
4. 浏览器地址栏、刷新、前进、后退语义保持正确。
5. 普通直达访问和首次加载仍然返回完整页面。
6. 不引入前端路由器，不引入新的前端框架，不做全局状态管理改造。

## 5. 设计决策

### 5.1 总体策略

采用“共享布局层 HTMX fragment 导航”方案。

核心原则如下：

1. 普通请求仍返回完整页面。
2. 共享布局导航默认优先采用 `hx-boost`，而不是逐链接手写 `hx-get`。
3. HTMX 请求只返回布局内必要片段。
4. sidebar 激活态继续由后端根据 URL 计算。
5. 通过 OOB 更新把新的 sidebar 状态刷回旧页面。
6. header 是否一起接入同一机制，视动态内容同步复杂度决定。

### 5.2 第一优先级：Sidebar 子菜单局部导航

sidebar 子菜单导航是本次改造的第一优先级。

原因是：

1. 这是当前用户最明显感知到“整页换页”的场景。
2. 这是共享布局内最稳定、最适合先做局部导航的区域。
3. 其激活态本来就由后端计算，最适合通过 OOB 更新同步。

因此，本 spec 要求：

1. 使用共享布局的模块内导航，应优先通过 sidebar 子菜单驱动 main content 切换。
2. sidebar 子菜单应优先采用基于 `hx-boost` 的 fragment 导航，而非完整页面跳转。
3. main content 应成为局部替换目标。
4. sidebar 应作为独立片段通过 OOB 更新，以同步激活态。

### 5.3 Header 一级导航的处理原则

header 一级导航可以接入同一套机制，但不作为首阶段硬性要求。

原因是 header 除了导航高亮，还可能同时包含：

1. 活动账户摘要。
2. 风险事件中心。
3. 告警计数。
4. 其它需要在切换时同步更新的动态块。

因此，本 spec 采用以下决策：

1. header 一级导航与 sidebar 使用同一技术路线。
2. 是否在同一轮实施，由复杂度决定。
3. 如果 header 动态内容同步代价较高，则允许首阶段保留普通导航。
4. 不允许因为 header 暂缓接入，就否定 sidebar fragment 导航的优先实施。

### 5.4 后端分流原则

后端必须在布局层区分 HTMX 请求与普通请求。

分流依据：

1. `HX-Request`。
2. 必要时可补充 `HX-Boosted`。

分流结果：

1. 普通请求返回完整页面。
2. HTMX 请求返回 main content fragment。
3. HTMX 请求可附带 sidebar 的 OOB 更新。
4. HTMX 导航必须保证地址栏、刷新、前进、后退语义正确；必要时应显式设置 `hx-push-url="true"`。
5. 如果 header 一并接入，则 HTMX 请求还可附带 header 的 OOB 更新。

### 5.5 Sidebar 激活态同步原则

sidebar 激活态继续由后端根据当前 URL 计算，不由前端自行推断业务状态。

实现语义必须满足：

1. 局部导航发生后，后端按新 URL 重新生成 sidebar。
2. 响应中通过 `hx-swap-oob="outerHTML"` 替换现有 sidebar。
3. 新激活项显示强调色，原激活项自动移除强调色。
4. 不引入额外前端业务状态管理来维护 sidebar 激活态。

### 5.6 普通访问语义保留

fragment 导航只能作为共享布局层的增强能力，不能破坏 SSR 和普通页面访问语义。

因此必须保留：

1. 首次访问返回完整页面。
2. 浏览器刷新返回完整页面。
3. 用户直接输入 URL 返回完整页面。
4. 浏览器前进、后退行为保持正常。

### 5.7 Fragment 导航后的滚动语义

fragment 导航完成后，必须定义统一的滚动行为。

默认约束如下：

1. 模块级导航完成后，`main content` 容器回到顶部。
2. header 与 sidebar 保持位置稳定，不因 fragment 导航发生额外滚动。
3. 仅对页内 tab、日志刷新、表格分页等“同一功能上下文内的局部更新”允许保留当前滚动位置。
4. 若某页面需要偏离该默认规则，必须在对应 spec 中单独说明。

## 6. 实现方案

### 6.1 共享布局层

在 `quantide/web/layouts/main.py` 中统一承担 fragment 导航分流逻辑。

要求：

1. 为 header、sidebar、main content 提供稳定容器 ID。
2. 布局渲染入口统一识别 `HX-Request`。
3. 普通请求返回完整页面。
4. HTMX 请求返回 main content 片段，并附带 sidebar OOB 更新。
5. 如果 header 一并接入，则补充 header OOB 更新。

本 spec 不允许要求每个业务页面单独维护一套 fragment/page 双分支渲染逻辑；布局层应成为统一入口。

本 spec 也不允许通过中间件解析或改写 HTML 响应体来实现 fragment 导航；full-page / fragment 分流必须发生在布局渲染层或共享辅助函数中。

### 6.2 Sidebar 组件

在 `quantide/web/components/sidebar.py` 中保持现有结构和后端激活态计算方式不变，只做最小增强。

要求：

1. sidebar 根容器具有稳定 ID。
2. sidebar 导航默认优先采用 `hx-boost`。
3. sidebar 激活态仍由后端根据 URL 计算。
4. sidebar 支持作为完整片段被 OOB 替换。
5. 不额外增加前端状态管理逻辑。

### 6.3 Header 组件

在 `quantide/web/components/header.py` 中是否启用 fragment 导航，取决于首轮实施评估结果。

若同轮接入，则要求：

1. 一级导航优先采用 `hx-boost` 支持 fragment 导航。
2. 激活态继续由后端根据 URL 计算。
3. header 中动态摘要块通过 OOB 同步。
4. 不允许在前端维护与业务绑定的 header 状态。

若不同轮接入，则允许首阶段保持普通导航，但必须保证 sidebar 子菜单 fragment 导航不受影响。

### 6.4 业务页面

业务页面应继续负责：

1. 生成 main content。
2. 设置当前 header/sidebar 的 active 语义。
3. 在共享布局层之上渲染自身内容。

业务页面不应各自实现一套导航框架。

首批适合接入的页面优先级如下：

1. `system/*`。
2. `strategy`。
3. 其它 sidebar 子菜单切换频繁的页面。

## 7. 非目标

本 spec 明确不包含以下内容：

1. 引入 React、Vue 等前端框架。
2. 引入客户端路由器。
3. 重写全局状态管理。
4. 将 quantIDE 改造成完全前端 SPA。
5. 业务页内部的大规模组件重构。
6. 仅通过动画或 loading bar 掩盖整页重绘，而不改变导航机制。

## 8. 验收标准

### 8.1 Sidebar 子菜单切换

1. 点击数据维护下相邻子菜单时，header 不应整块闪烁。
2. main content 应局部切换，而不是表现为整页刷新。
3. sidebar 激活项应准确切换，旧高亮不残留。

### 8.2 URL 与浏览器行为

1. 地址栏应正确变化。
2. 刷新后仍能落在对应页面。
3. 浏览器前进、后退应正常工作。

### 8.3 Fragment 导航后的滚动行为

1. 模块级 fragment 导航完成后，main content 默认回到顶部。
2. header 和 sidebar 不应发生额外滚动。
3. 保留滚动位置的例外场景必须在对应 spec 中明确说明。

### 8.4 完整页面语义

1. 普通直达访问仍返回完整页面。
2. 首次加载仍返回完整页面。
3. 未接入 fragment 导航的页面不得因本改造而损坏现有访问行为。

### 8.5 Header 条件性验收

若 header 一级导航同轮接入，则额外要求：

1. header 本身不应整块闪烁。
2. 顶部激活项切换正确。
3. 账户摘要、告警中心等动态块同步正确。
4. 不因局部导航导致 header 状态残留或错位。
