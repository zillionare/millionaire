## 3. 确认的问题

### R01 · P1：插件发现直接执行导入，坏插件可中断扫描或长期占住调用线程

- 位置：`quantide/factors/plugins.py:150`（尤其 161）、`:230`、`:270`；Web 风洞入口 `quantide/web/pages/factors.py:803`；执行器 `quantide/service/process_runner.py:71`。
- 对应：FR-5001、NFR-5002、AC-5002。
- 发现器直接在调用进程执行 `exec_module`，只捕获 `Exception`，没有导入时限。合法文件与 `raise SystemExit(7)` 共存时，真实扫描进程退出 7，没有返回 skipped；换成顶层 `time.sleep(60)`，扫描超过外层 4 秒限时，被测试 harness 终止。服务启动调用链可能退出；请求调用链会被异常/阻塞打断。不能笼统声称“每个 SystemExit 一定杀死整个 Web 进程”，但“不影响服务/内置因子”的契约已经不成立。
- Web/CLI 风洞也有直接同步运行路径；AI 的部分重计算使用子进程，并不覆盖枚举及这些入口。此外，`run_isolated` 只有 timeout/cancel，接口和实现均无内存预算，未满足 NFR-5002。
- 修复：隔离枚举与计算，所有正式入口共用有界执行器；坏导入、异常退出、超时、超内存转为结构化诊断。仅扩大到 `except BaseException` 不能解决挂起。此要求是故障隔离，不等价于为任意 Python 提供安全沙箱。
- 验收：合法插件与 SystemExit/阻塞导入/无限计算并存时，主服务及健康页仍响应；逐个诊断且进程回收。内存超额用受控、小额度场景验证，避免压垮宿主。
- 证据：`repros/import_isolation.log`；脚本 `opencode-repros/repro_a_plugin_isolation.py`。

### R02 · P1：同一插件缓存可掩盖前视，风洞未执行要求的冷/热缓存交叉检验

- 位置：`quantide/audit/plugin_factor.py:231`、`:458`。
- 对应：FR-5002、AC-5004、AC-5005。
- 契约、隔离、重复运行、所有未来扰动共用一个插件 compute 对象和模块全局状态。反例按证券缓存首次调用的**全样本 close 均值**，后续忽略输入变化；各项检查全部 PASS。清空缓存后仅改未来价格，历史输出立即改变，独立冷启动结果明确证明存在前视。
- 修复：每个基准/扰动分支能从相同的干净初始状态独立运行，同时另测有意预热后的路径；子进程外壳只包住整次审计并不够，内部仍可能共享缓存。报告记录冷/热分支、截断点、扰动行数与摘要。
- 验收：本反例 FAIL；无缓存与合法缓存因子都能通过；不得通过禁用所有缓存或跳过某个分支凑 PASS。
- 证据：`repros/audit_evidence.py`、`.log` 中 `memo_full_sample_future_leak=PASS`、`cold_cache_oracle.past_equal=false`。

### R03 · P1：源码变化已改变模型键，特征面板缓存却仍命中旧公式

- 位置：`quantide/strategies/example/ml_momentum_reversal.py:570`、`:639`、`:647`。
- 对应：FR-5001、NFR-5003、AC-5003。
- `_panel_cache_key` 含因子名，不含其内容版本；实例自身的缓存早退也不检查版本。修改外部插件公式后，catalog version 和新策略的 model key 变化，但面板 key 不变，新策略取到模块缓存的旧特征。结果是“新模型身份 + 旧公式数据”，徽章变 STALE 并不能修复这份训练输入。
- 修复：缓存身份纳入选中因子及依赖版本，覆盖模块缓存与实例缓存；模型、解释和标签缓存一并检查依赖身份。避免只在 UI 扫描时清理一个缓存。
- 验收：同进程连续运行 A 公式、修改为 B、创建新策略及重用实例，两条路径均必须重算并使用 B；解释不能继续引用 A 的特征。
- 证据：`repros/source_cache.py`、`.log`：`catalog_version_changed=true`、`model_key_changed=true`、`panel_cache_key_changed=false`、`old_cached_value_reused=true`。

### R04 · P1：30m 影子首槽缺数据或首次延迟调度时会永久漏槽

- 位置：`quantide/service/shadow_intraday.py:133`（`last is None` 时 `cursor=latest`）。
- 对应：FR-5012、AC-5019、AC-5020。
- 初始没有成功槽位时，游标不使用开始边界或已有 gap。10:00 缺数据留下 gap，10:30 运行时直接处理 10:30，10:00 不再补算；第一次调用延迟到 11:00 时，仅处理 11:00，前两个槽位连 gap 都没有。常见的历史数据迟到就能触发，无需非常规故障。
- 修复：持久化精确启用边界/首个应回放槽，从最早未完成槽有序推进；首个缺口也必须阻断后续槽，重启/延迟调用不能重置起点。
- 验收：首槽迟到、首次任务延迟、第一笔提交前退出、跨日重启均与独立槽位账本一致；历史 ready 后全部补回且不重复下单。
- 证据：`repros/shadow_intraday.log` 的 `missing_1000_ready_1030`、`first_schedule_at_1100`；脚本 `opencode-repros/repro_c_shadow_intraday.py`。日历和策略计算被 stub，真实执行了游标、分钟读取、SQLite 写入路径。

### R05 · P1：补算旧 bar 的 actual 快照来自当前账户，历史对照事实失真

- 位置：`quantide/service/shadow_intraday.py:155`、`:253`。
- 对应：FR-5012、AC-5019、AC-5020。
- `_actual_bar` 不按 bar_slot 查询历史事实，直接读当前 `runtime.broker.asset/positions`。例如账户已经变为 9000 元，再补算 10:00 和 10:30，两个旧槽 actual cash 都写成 9000；交易列表和模型 hash 还被固定写为空。由此产生的逐 bar 差额不能用来解释当时执行偏差。
- 修复：actual 在真实运行推进时独立落盘，按有效时刻保存账户、交易和模型引用；shadow 回补读取已保存事实。缺少历史实际事实时明确标记缺失，不能用当前账户填充旧时间戳。
- 验收：两个槽间发生交易，稍后回补影子，actual 必须保留各自不同的历史状态；重启后相同。核对逐 bar 实际成交与模型引用。
- 证据：`repros/shadow_intraday.log` 的 `backfill_actual_bar`。

### R06 · P1：消融没有锁定完整的有效股票池/执行条件

- 位置：`quantide/service/research_backtest.py:328`、`:390`、`:275`。
- 对应：FR-5004、AC-5008。
- baseline 使用内置默认参数、没有嵌套 universe_filter 时，会从 fixed 中删去该键，variant 自己的嵌套过滤条件得以保留。即使显式指定相同 universe_filter，symbols、universe_mode、universe_size、index_pool_codes 等仍可不同。费用锁定也没有包含滑点，预设可带不同 slippage_pct。UI 却声称同一 PIT 规则与费用。
- 主审进一步使用**真实 MLMomentumReversalStrategy 默认配置和真实配置合并**复现，未替换策略解析；只替换执行回测/指标采集：baseline 默认 60 日上市规则与 variant 的 120 日规则未统一；显式 universe_filter 相同也不能统一不同 symbols、规模和选池模式。
- 修复：先解析 baseline 的完整有效 Universe/Execution 配置，再统一固定并持久化，或拒绝冲突；不能只复制一个可能为空的字典。允许变化的因子/标签/训练超参需单独明确。报告记录最终生效值。
- 验收：不同层级/别名的冲突选池配置，以及不同滑点均被拒绝或统一；真正消融只改变指定变量。
- 证据：`repros/ablation_real_defaults.py`、`.log`；初步委托证据 `opencode-repros/repro_b.log`。

### R07 · P1：历史回测的风洞徽章会借用后来新公式的 PASS

- 位置：`quantide/service/factor_audit.py:364`，尤其 `:380`；重新体检入口 `quantide/web/pages/strategy_report_views.py:261`。
- 对应：FR-5007、NFR-5003、AC-5013。
- 回测徽章只取“当前这些因子的最新审计”，没有和回测当时的源码、模型、配置和数据绑定。A 公式完成旧实验后改成 B，再对 B 审计通过，旧回测页会显示 B 的 PASS，导出的证据也是最新报告。此时页面上的 PASS 并不证明旧实验。
- 修复：回测创建时保存不可变依赖清单与审计报告引用，徽章对照实验绑定身份；重新审计当前公式应产生新证据/新实验，不能回填旧实验。取不到旧实验身份时应 UNVERIFIED/证据缺失。
- 验收：A 回测 → B 修改 → B 重检 PASS，A 的绑定记录和证据不被覆盖；只有完全匹配的证据才赋予对应实验 PASS。
- 证据：`repros/interval_badge.py`、`.log` 中 `old_backtest_new_audit`，旧/新 source hash 不同但旧回测徽章 PASS 且引用新 run_id。反例用固定的旧实验因子列表隔离测试徽章归属，未运行第二次完整 ML 回测。

### R08 · P2：DataFrame 输出丢行/多键被左连接掩盖，契约检查仍 PASS

- 位置：`quantide/factors/plugins.py:365`，尤其 `:372`。

### R09 · P2：重复复权坏因子仍 PASS，AC 的保证需要可判定契约

### R10 · P2：PIT 单日接口的成交额兜底可读取未来，降级诊断也未贯通报告

- 位置：`quantide/factors/universe.py:230`、`:281`、`:308`；调用端 `quantide/strategies/example/_ml_support.py:731`；`quantide/factors/alphatest.py:459`。

### R11 · P2：因子周期未在统一目录/默认 ML 选择中隔离，30m 插件能破坏日线回测

- 位置：`quantide/factors/registry.py:143`、`:198`；`quantide/web/pages/strategy_backtest_views.py:419`；`quantide/service/factor_wind_tunnel.py:69`。

## 4. 需求本身的评估与需要明确的合同

需求方向成立：免 Token 体验解决首次使用，单文件插件解决扩展入口，风洞与正交性约束 AI 产物，预设与消融衡量增量价值，Shadow-Run 继续核对执行偏差。这些工作包都在本次 FR/AC 中，不能在实施结束后不加说明地转称“下一里程碑”。

发布前建议把以下合同写得更精确，避免继续出现“实现看似满足、实际无法验收”：

1. **风洞 PASS 的范围**：限定为明确样本、截断点、缓存初始状态、计算版本和测试合同下通过。有限扰动无法证明任意 Python 公式无错；重复复权尤其需要价格 provenance/独立 oracle（R09）。保留宣传口吻，同时不把 PASS 扩展成策略正确性或收益保证。
2. **输入身份**：统一定义 factor source/dependency、数据选择范围、interval、有效选池与执行参数、模型、审计配置的身份清单。分别用于缓存、实验记录、徽章和导出，不能各自拼一个近似 hash。尤其区分“当前公式通过”与“历史实验绑定证据”。
3. **周期与可得时刻**：规格允许 1d/30m/1M 元数据，需明确每个周期在哪些 CLI/Web/ML 路径受支持；分钟截断点不能仅按自然日理解；声明 next_open 的值何时允许进入信号，也应在计算/消费合同中明确。
4. **训练标签与合格池**：写清 raw_return 向后兼容与上游 v0.4 成熟合同的关系，暂停/缺行时 h 个交易日是否依据权威日历，以及每个历史信号日合格池的形成位置。现有同日排名算子正确，不足以独自证明整条训练路径已经遵守这些前提。应增加缺行、退市/ST 变更与不同成熟日期的独立 oracle。
5. **资源与取消**：明确枚举、模型请求、计算进程各自的时限、内存预算、取消 SLA、恢复语义和诊断码。白名单文件工具的路径边界不等同于任意 Python 插件的 OS 安全沙箱；两者应清楚区分。
6. **消融控制变量**：固定完整的有效选池/执行合同，允许变化项明确列出。滑点、symbols、指数池与成交时序不能意外成为“新增因子效果”。
7. **证据完成标准**：AC 必须有真实路径证据；规划中的工作包顺序不构成对缺失 AC 的自动豁免。维护完成表时显式注明实现、单测、集成、跨平台/现场验证四类状态。

这些是合同补强建议；除 R09 所述可判定性问题外，不能用“需求还可更精确”来豁免已经明确的 AC。
